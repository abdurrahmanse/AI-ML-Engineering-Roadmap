Level 9 · High-Performance Computing (HPC) & Scaled Research Systems

Phase: HPC Clusters, Scaling & Explainability
Suggested duration: 13 sessions (~3 weeks)
Prerequisites: Level 8 (Experimental Design, Ablation Studies & Fair Benchmarking)
Scope: Transition research codebases from single-GPU workstations to university and supercomputing HPC clusters: navigating SLURM batch job schedulers, environment modules, distributed multi-node execution with PyTorch Fully Sharded Data Parallel (FSDP), DeepSpeed ZeRO-3, and Megatron tensor parallelism; profiling Model FLOPs Utilization (MFU), optimizing NCCL communication collectives, and overcoming out-of-memory (OOM) bottlenecks.

M9.1 · Supercomputing Infrastructure: SLURM, Environment Modules & Interconnects — (sessions: 2)
Session 1 · SLURM Workload Management & Batch Scheduling
- Master university and national supercomputing job scheduling using SLURM (Simple Linux Utility for Resource Management).
- Author modular SLURM batch scripts (#SBATCH directives): configuring nodes, tasks-per-node, GPU partitions, time limits, and memory requests.
- Manage large-scale hyperparameter searches and multi-seed sweeps efficiently using SLURM job arrays (--array) with automated output redirection.
Session 2 · HPC Software Modules & High-Speed Network Fabrics
- Navigate HPC software module systems (Lmod, Environment Modules): loading compiler toolchains, specific CUDA drivers, and optimized cuDNN libraries.
- Understand supercomputing network topologies: high-bandwidth InfiniBand (HDR/NDR) fabrics and RoCE (RDMA over Converged Ethernet).
- Leverage GPUDirect RDMA (Remote Direct Memory Access) to enable zero-copy GPU-to-GPU data transfers across physical server nodes.
Mental model: SLURM is the traffic controller of the supercomputer; precise resource specifications prevent jobs from failing due to memory or time preemption.
Try: Write a SLURM batch submission script requesting 2 nodes and 8 GPUs with automated checkpoint recovery and email alerts upon job completion.
Outcome: Navigate university and laboratory supercomputing environments, submit multi-node batch scripts, and leverage high-speed interconnects.

M9.2 · Distributed Data Parallelism: DDP, FSDP & DeepSpeed ZeRO — (sessions: 2)
Session 1 · DistributedDataParallel (DDP) & Ring All-Reduce
- Master PyTorch DistributedDataParallel (DDP): multi-process spawning, local rank vs. global rank mapping, and distributed process group initialization.
- Analyze the Ring All-Reduce communication algorithm: synchronizing parameter gradients across N GPUs with 2*(N-1)/N communication volume.
- Implement gradient accumulation to simulate large global batch sizes on hardware with restricted physical VRAM capacity.
Session 2 · Zero Redundancy Optimizer (ZeRO) & PyTorch FSDP
- Deconstruct DeepSpeed ZeRO memory sharding: ZeRO-Stage 1 (sharding optimizer states), ZeRO-Stage 2 (gradients), and ZeRO-Stage 3 (model parameters).
- Master PyTorch Fully Sharded Data Parallel (FSDP): configuring sharding strategies (FULL_SHARD, SHARD_GRAD_OP, NO_SHARD), mixed precision, and backward prefetching.
- Overcome out-of-memory (OOM) errors when scaling model parameters beyond the physical memory capacity of individual GPU cards.
Mental model: Standard DDP duplicates the entire model on every GPU; FSDP shards model parameters and optimizer states across the cluster, reconstituting them on-the-fly.
Try: Convert a standard PyTorch training loop to PyTorch FSDP, training a multi-billion parameter model across multiple GPUs with mixed precision.
Outcome: Implement and scale distributed data-parallel training across multi-GPU and multi-node clusters using DDP and FSDP.

M9.3 · Model, Pipeline & Tensor Parallelism (Megatron-LM) — (sessions: 2)
Session 1 · Tensor Parallelism & Matrix Partitioning
- Master intra-layer tensor parallelism (Megatron-LM): splitting linear weight matrices across GPU devices to distribute memory and computation.
- Implement Column Parallel Linear layers (splitting attention QKV projections) and Row Parallel Linear layers (merging projections with all-reduce).
- Maintain communication efficiency: inserting exactly two all-reduce operations per Transformer layer (one in self-attention, one in MLP block).
Session 2 · Pipeline Parallelism & Activation Checkpointing
- Implement inter-layer pipeline parallelism (PP): partitioning sequential Transformer layers across distinct physical GPUs.
- Analyze pipeline bubbles and execution schedules: standard sequential schedules vs. interleaved One-Forward-One-Backward (1F1B) schedules.
- Apply activation checkpointing (gradient checkpointing): trading 30% additional compute to discard intermediate activations and recompute them during backward passes.
Mental model: Tensor parallelism splits individual layers horizontally across GPUs; pipeline parallelism stacks layers vertically across a chain of GPUs.
Try: Implement column-parallel and row-parallel linear layers in PyTorch using distributed communication collectives, verifying numerical equivalence with a monolithic layer.
Outcome: Design and execute 3D parallelism (Data + Tensor + Pipeline Parallelism) to train ultra-large models exceeding single-device memory limits.

M9.4 · Communication Collectives & Hardware Bottleneck Profiling — (sessions: 2)
Session 1 · Distributed Communication Collectives (NCCL)
- Master fundamental communication primitives in NCCL (NVIDIA Collective Communications Library): All-Reduce, Reduce-Scatter, All-Gather, and Broadcast.
- Benchmark inter-GPU communication bandwidth: measuring NVLink intra-node bandwidth (up to 900 GB/s) versus InfiniBand inter-node bandwidth.
- Implement communication-computation overlapping: prefetching next-layer parameters asynchronously while current-layer matrix multiplications execute.
Session 2 · Hardware Diagnostics & PyTorch Profiler
- Profile distributed execution using PyTorch Profiler and NVIDIA Nsight Systems (nsys): recording kernel timelines and communication overhead.
- Inspect execution traces using Chrome Trace Viewer and TensorBoard: identifying GPU idle bubbles caused by CPU data loading stalls or slow NCCL barriers.
- Diagnose and eliminate straggler nodes: detecting thermal throttling, slow network ports, or uneven batch workloads across distributed workers.
Mental model: A distributed cluster is only as fast as its slowest worker; profiling traces expose hidden synchronization barriers where GPUs sit idle.
Try: Profile a multi-GPU training run using PyTorch Profiler, export the JSON trace, and identify the exact percentage of time spent in NCCL communication.
Outcome: Profile distributed multi-GPU training runs, diagnose communication bottlenecks, and optimize computation-communication overlapping.

M9.5 · Model FLOPs Utilization (MFU) & Computational Scaling Efficiency — (sessions: 2)
Session 1 · Calculating Theoretical & Achieved FLOPs
- Calculate theoretical peak hardware floating-point operations (FLOP/s) for NVIDIA GPUs (e.g., A100: 312 TFLOPs BF16; H100: 989 TFLOPs BF16).
- Formulate precise model FLOP formulas: calculating floating-point operations per training token (approximately 6 * P * N FLOPs per forward-backward pass).
- Measure Achieved Model FLOPs Utilization (MFU) (Chowdhery et al.): computing the ratio of achieved throughput to peak theoretical hardware capacity.
Session 2 · Scaling Efficiency & Weak vs. Strong Scaling
- Evaluate strong scaling: measuring training speedup as GPU count increases for a fixed global problem and batch size.
- Evaluate weak scaling: measuring throughput maintenance as both GPU count and global problem size scale proportionally.
- Target elite research efficiency standards: tuning distributed batch sizes, sequence lengths, and precision to achieve > 45-55% MFU on production clusters.
Mental model: MFU is the definitive research metric of systems efficiency, proving whether your codebase is actually extracting hardware capability.
Try: Write a Python script that calculates the exact theoretical MFU of a Transformer training run based on logged tokens-per-second and GPU hardware specs.
Outcome: Quantify Model FLOPs Utilization (MFU) and systematically evaluate strong and weak scaling efficiency on research supercomputers.

M9.6 · Capstone Project: Distributed Multi-Node HPC Training & Scaling Benchmark Harness — (sessions: 3)
Session 1 · Multi-Node SLURM Architecture & Distributed Launcher
- Build an automated, production-ready distributed training harness designed for multi-GPU and multi-node university HPC clusters.
- Author robust SLURM submission scripts featuring dynamic rendezvous (torchrun with master node IP/port discovery and SLURM environment variables).
- Implement PyTorch FSDP with mixed-precision (BF16), activation checkpointing, and backward prefetching configured for scalable execution.
Session 2 · Scaling Benchmark, MFU Profiling & Scientific Reporting
- Execute a rigorous scaling study benchmarking throughput across 1, 2, 4, and 8 GPUs (or multi-node setups where available).
- Measure and plot weak and strong scaling curves, tracking achieved MFU, communication-to-computation ratios, and peak VRAM allocation.
- Package the harness into a reusable template repository featuring automated node diagnostics, checkpoint recovery, and LaTeX scaling table generators.
Mental model: Research institutions evaluate PhD candidates and RAs on their ability to command supercomputing clusters efficiently without wasting compute allocations.
Try: Execute the distributed training run across multiple GPUs, generate the scaling efficiency curve, and calculate final MFU metrics.
Outcome: Deliver a fully audited, publication-grade distributed training harness and scaling report running seamlessly on high-performance computing clusters.

CAPSTONE PROJECT: Distributed Multi-Node HPC Training & Scaling Benchmark Harness

- Collects detailed runtime telemetry: tokens processed per second, step latency, peak VRAM allocation, and NCCL communication time.

Deliverables:
- Modular distributed codebase (hpc_distributed_harness/) with clean SLURM sbatch scripts and configuration files.
- Automated profiling report generated via PyTorch Profiler with Chrome trace exports.
- High-resolution vector plot displaying weak and strong scaling efficiency alongside ideal linear scaling lines.
- Formal 3-page HPC systems report detailing cluster specifications, MFU calculations, and distributed scaling analysis.
Outcome: You can scale complex deep learning models across university and supercomputing clusters with verified systems efficiency and reproducible performance.
